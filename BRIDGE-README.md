# Переделка прототипа в визуальное семейство ONE PSIM

Что это: один файл `bridge.css`, подключённый в `schedule_v6.html` после собственных стилей
прототипа. Разметка, JS и адаптив для переделки не менялись — единственная правка JS в v6
относится к другому дефекту (перескок прокрутки, раздел 8).

**Источник правил.** `ONE.PSIM.PrototypeKit`: `AGENTS.md`, `docs/DECISIONS.md`,
`docs/RESTYLE-RULES.md` §0–§4. Лестницы состояний дополнительно сверены с собственной
транскрипцией кита — `src/theme/tailwind.css`, слой `@layer components`: он сгенерирован из того же
`oneTheme.ts`, что и §2 (D-027), поэтому расхождения между двумя источниками видны сразу. Все
найденные расхождения перечислены в разделе 7.

**Файлы**

| Файл | Что это |
|---|---|
| `bridge.css` | 94 правила: карта токенов §1 + лестницы §2. Ни одного hex в объявлениях |
| `theme/one-psim.css` | Копия из кита. Две правки селекторов — см. раздел 5, решение 1 |
| `theme/native.css` | Копия из кита без изменений |
| `schedule_v6.html` | Прототип: `<link rel="stylesheet" href="bridge.css">` после `</style>` |
| `_dev/check_bridge.js` | Проверка bridge: синтаксис, разрешимость токенов, существование селекторов |
| `_dev/check_contrast.js` | Контраст всех пар «текст на заливке», о которых bridge принимает решение |
| `_dev/test_v6_scroll.js` | Проверка исправления прокрутки и обвязки переделки |

`bridge.css` подойдёт и для `schedule_v5.html` — словарь классов у v5 и v6 одинаковый, v6 добавил
только атрибуты. Подключён он только в v6, как в актуальную версию.

## 1. Диагностика перед правками (§0)

| Проверка | Результат |
|---|---|
| Слой переменных (§0.1) | Есть: `:root,[data-scheme=light]`, `[data-scheme=dark]` — цвета; отдельный `:root` — геометрия и размеры |
| Переменных | 53 (37 из них цвет/шрифт), 303 обращения `var()` в CSS + 4 в JS |
| hex вне слоя переменных (§0.2) | **4 из 74 (5,4 %)** — ниже порога ~10 %, поэтому выносить цвета перед bridge не требовалось |
| Как переменные потребляются (§0.3) | Разобрано по ролям, см. ниже — одна переменная красит три разные роли |
| Состояния, меняющие цвет (§0.4) | 44 селектора состояний собраны и каждое разобрано по §2 |
| Скриншоты «до» (§0.5) | Отдельных снимков не делал — задача это исключает. Роль оригиналов играют `shots/v5-*.png` из предыдущей итерации: v6 до подключения bridge визуально идентичен v5 |

**Главная находка §0.3.** `--border-default` (28 обращений) красит **три** разные роли:

- границы между регионами — нижний край шапки, край заголовка панели, сплиттеры колонок, рамки
  панелей, `pre.json`, рамка карточки;
- разделители строк внутри списков — `.drow`, `.rule`, `table.tbl td`;
- рамки контролов — `.pill--idle`, `.chip`.

По §1 это три разных токена, поэтому в bridge переменная переведена на роль границы региона
(доминирующую), а два других потребителя перекрыты точечно. Аналогично `--border-strong` оказался
рамкой контрола **в покое**, а не hover-состоянием, поэтому он ушёл в `--one-border`, а hover
`.cal__cell` получил `--one-border-strong` отдельным правилом.

Вторая находка: `.lbl` тоже служит двум ролям — подпись поля и заголовок секции в правой панели.
Разделены селектором `.insp__sec > .lbl` (заголовок) против остальных `.lbl` (подпись поля).

**Переключатели (§2.4 / D-018).** У прототипа их четыре группы — 24ч/12ч, тип расписания,
инструмент рисования, шаг привязки, плюс фильтр дней недели. Все уже были на заливке `accent` с
подписью `accent-on`, то есть на лестнице primary. Добавлены только hover и pressed. Светло-голубой
заливки, которой в ONE PSIM нет, в прототипе не было изначально.

**Нативные контролы (§2.13 / D-040).** `native.css` подключён после `one-psim.css`. Прототип
**не содержит ни одного правила для `input`** — ни `input { }`, ни `input[type=…]`, ни
`appearance: auto`, ни `accent-color`. Поэтому типовой гибрид из §2.13 (браузерная галочка, потому
что `(0,1,1)` бьёт `:where()`) здесь возникнуть не может, и строка
`input[type="checkbox"], input[type="radio"] { appearance: none }` **не понадобилась** — я её не
добавлял, чтобы не держать в bridge правило без причины. Радио и switch в прототипе отсутствуют,
эти секции `native.css` просто не срабатывают; файл оставлен дословной копией, чтобы его можно было
обновлять из кита.

Чекбоксы прототипа (4 места: отметка строки сетки, цели копирования, «ежегодно», «цикличный»)
получают лестницу DS без классов. Их размер меняется с браузерного (~13px) на 18px по §2.13 —
в ячейке отметки 30px помещается.

## 4. Чего намеренно не касался (§2.11)

- Компоновку, плотность, поведение, адаптив, размеры шрифтов вне ролей DS.
- **Базовый размер текста остаётся 12px** (`--fs-ctl`), при 14px body-md в дизайн-системе. Прототип
  заметно плотнее DS; D-004 это прямо разрешает, а смена базового размера переложила бы всю сетку.
- Шкалу `--fs-cap: 9px … --fs-h2: 16px` — кроме элементов с ролью DS (пункт 12–14 выше).
- Геометрию: высоты 28/24px у контролов, 26px у пунктов меню (в DS 32px — см. вопрос 3),
  сетку на 24 часа, ширины колонок.
- Иконочное семейство — текстовые глифы прототипа (`✎ ⌫ ↶ ↷ ⋯ ▾ ↻ 🗑`) остались своими: §2.11 прямо
  говорит не менять иконки.
- Три `#fff` и один `#ffffff26` вне слоя переменных: 4 значения, ниже порога §2.11.
- `--r-xs: 2px` (радиус полосок-превью) — в DS нет аналога.
- z-index попапов (60/55/80): порядок «страница < scrim < попап < диалог» уже соответствует §2.9b,
  переписывать числа незачем.

## 5. Решения, которые принял сам

**1. Как тема DS сцеплена с переключателем прототипа.** Прототип переключает схему через
`body[data-scheme="light"|"dark"]`, а `one-psim.css` объявляет токены на `:root,[data-theme="light"]`
и `[data-theme="dark"]`. Без сцепки тёмные токены не применились бы никогда. Варианты были три:
продублировать в bridge весь тёмный блок (≈80 строк значений — при обновлении DS гарантированно
устареет), добавить атрибут в разметку или строку в JS (запрещено задачей), либо расширить два
селектора в **локальной** копии темы. Выбрал третье:

```css
:root, [data-theme="light"], [data-scheme="light"] { … }
[data-theme="dark"],  [data-scheme="dark"]         { … }
```

Значения не тронуты, правка помечена комментарием в файле. При обновлении из кита нужно повторить
ровно эти две правки. Задача разрешает править локальные копии темы («убери из native.css этот
элемент»), поэтому считаю это допустимым, но более чистое решение — за владельцем (вопрос 1).

**2. Радиусы — по `kit.css`, а не по таблице §1.** §1 говорит «`--one-radius-window` (карточки,
диалоги) / `--one-radius-container` (контролы)», то есть контролы 6px. Но `kit.css` даёт
`.btn`, `.field`, `.tab` радиус `--one-radius-control` (4px), а `.card` — `window` (8px). Взял
`kit.css`: это транскрипция самих компонентов, и у прототипа контролы уже 4px — визуально ничего не
меняется. Панели выросли с 6px до 8px. Расхождение вынесено в раздел 7.

**3. Warning в тексте — `--one-warning-icon`, а не `--one-warning`.** §1 перечисляет для текста и
индикаторов `--one-info, --one-success-icon, --one-warning, --one-danger`. У success взят шаг
`-icon` именно потому, что `--one-success` (#20D300) как текст нечитаем — измерено **1,8:1** на
`surface-muted` в Light против 4,5:1 у `-icon`. У warning ровно та же картина: `--one-warning`
(#FF8A00) даёт **2,1:1**, а `--one-warning-icon` (#995300) — **5,1:1**; в Dark оба равны #FF8A00
(6,5:1). Применил `-icon` к тексту (строка состояния, глиф предупреждения), оставив `--one-warning`
для заливок и линий. Считаю это следованием логике §1, а не изобретением, но формально это моё
решение — см. вопрос 2. Числа считает `node _dev/check_contrast.js`.

**4. `.kindtag` — нейтральный бейдж.** Тип расписания («Недельное», «Круглосуточно») печатался
accent-цветом на accent-тинте, что D-020 запрещает как приём. Статусом тип не является, поэтому
тройку `info` брать неправильно; по D-039 цвет категории не должен совпадать со статусным, а рядом в
списке есть индикатор «активно сейчас». Взял лестницу `.badge-neutral` из `kit.css`:
`surface-subtle` + `fg-muted`.

**5. Роль `label` для подписей полей — самое заметное изменение плотности.** §2.13/D-028 требует
подпись поля 500 12/16 в `fg-muted` обычным регистром. У прототипа было 9px капсом с разрядкой, то
есть подпись растёт с ~12px до 16px по высоте. Это поднимает на пару пикселей панель типа
расписания, панель цикла и секции правой панели. Применил, потому что §2 требует брать лестницы
дословно, но если владелец предпочтёт плотность прототипа — это одна строка в `bridge.css`:
удалить блок `.lbl { font: var(--one-type-label); … }`.

**6. `kbd` — 1px по кругу.** §2.5 перечисляет контролы, и `kbd` в этот список не входит, но
рассуждение правила («2px в бледном цвете у прототипа, с серым ONE PSIM это тяжёлая рамка») к нему
применимо буквально: `--one-border` в Light — #8E8F96. Убрал эффект «клавиши» ради однородности.

**7. Заголовки колонок — роль `label-strong`.** «Строка / итог» в линейке сетки и дни недели в
календаре были 9–11px капсом с разрядкой. `kit.css` задаёт `.table th` как `600 12/16` в `fg-muted`
обычным регистром — это и есть заголовок колонки таблицы, взял его. Формально §2.2b/D-021 говорит
про заголовки **разделов**, не колонок, поэтому отношу к своим решениям.

**8. Стрелка `<select>` унифицирована.** `.langsel` рисовал стрелку двумя CSS-градиентами
(треугольник), остальные `select` получают от `native.css` шеврон. Перевёл оба на шеврон
`native.css` — одна форма на экране. Ассет взят из `native.css` без изменений.

**9. `.btn--danger` оставлен текстовой кнопкой.** У Button нет appearance `danger` (§2.12), а
палитра D-012 описывает **залитую** кнопку. Превращать текстовую кнопку «Удалить» в залитую красную
— это изменение веса кнопки, то есть UX-решение прототипа, которое §2.1/D-016 оставляет прототипу.
Перевёл только токены; подпись не меняет цвет ни в одном состоянии (D-022).

## 6. Вопросы владельцу

1. **Сцепка схемы.** Оставить правку двух селекторов в локальной копии `one-psim.css` (раздел 5,
   решение 1), или правильнее добавить в прототип `data-theme` рядом с `data-scheme` — одна строка
   JS? Второе чище при обновлениях DS. Третий вариант — генератор кита мог бы сразу писать в
   селекторы оба атрибута, и тогда переделка любого прототипа со своим переключателем тем не
   требовала бы правок вообще.
2. **Warning как текст.** Подтвердить решение 3 — брать для текста шаг `-icon`. Если да, это стоит
   дописать в §1 строкой «`--one-warning-icon`» рядом с `--one-success-icon`, иначе следующий агент
   повторит 2,2:1.
3. **Высота пункта меню.** §2.9a задаёт 32px, отступ 16px, зазор 12px — измеренные по Storybook.
   У прототипа пункты 26px с отступом 8px. Я не менял (§2.11 про плотность), но правило измеряет
   геометрию явно. Нужно ли приводить попапы к 32px, или геометрия остаётся свободой прототипа, как
   всё остальное по D-004?
4. **Базовая плотность.** Прототип живёт на 12px тексте против 14px body-md в DS. Это осознанно
   (D-004), но если для семейства важнее совпадение размеров — это отдельная итерация, меняющая
   компоновку, и её лучше делать не bridge'ем.
5. **Шрифт Inter не подключён.** `--one-font-ui` объявляет Inter первым, но файлов шрифта в проекте
   нет, и при открытии с диска подставится Segoe UI. В ките шрифты лежат в `src/fonts` и вшиваются
   на сборке (`npm run build --inline-remote-fonts`). Копировать `src/fonts` + `fonts.css` в проект
   сейчас или оставить до шага сборки?
6. **Подпись полей** — оставить роль DS (12px) или плотность прототипа (9px)? См. решение 5.

**Новые пробелы, которых в §2.12 нет:**

1. **Залитый бейдж-маркер.** `.cal__b` (номер сработавшего правила в клетке календаря), `.ovr__n`
   (номер правила в списке) и `.tabbadge--warn` — маленькие залитые чипы. Все `.badge-*` в `kit.css`
   тинтованные (`bg` + `text` тройки), залитой лестницы нет. Оставил как у прототипа: заливка
   `--one-warning`, подпись `#fff`. **Контраст 2,4:1 в обеих схемах** — цифры читаются плохо, но
   ровно так было и в v5, я это не ухудшил. Аналогично `.tabbadge` внутри выбранной вкладки: заливка
   `accent` + `accent-on` (4,7:1). Нужна лестница залитого бейджа-счётчика; палитровый вариант
   (`--one-palette-orange` + белая подпись, прямо разрешённый D-026 как 2,6:1) здесь не подходит,
   потому что по D-039 цвет категории не должен совпадать со статусным, а чип лежит именно на
   warning-тинте.
2. **Разделитель строк: §1 против `kit.css`.** §1 говорит «разделитель строк внутри списка →
   `--one-surface-subtle`». `kit.css` для `.table td` использует `--one-table-row-divider`
   (Light #D2D3D5 против #E7E7E9 — заметно чётче). Сетка дней — именно таблица. Следовал §1 (как
   просили — дословно), но для плотной таблицы вариант кита выглядит уместнее. Стоит договориться,
   какой источник главный, и дописать `--one-table-row-divider` в §1.
3. **Радиусы: §1 против `kit.css`.** §1 — «контролы → `radius-container`» (6px); `kit.css` —
   `.btn`/`.field` на `radius-control` (4px). Взял `kit.css` (решение 2). Строку §1 стоит уточнить.
4. **Прозрачность как приглушение вне контролов.** `.cal__cell--outside { opacity: .6 }` — дни вне
   срока действия. §2.8 запрещает `opacity` для **disabled контролов**; клетка календаря контролом
   не является, лестницы для «неактивных данных» в §2 нет. Оставил.
5. **Две ступени DS не дотягивают до порогов на светлой теме** — это наблюдение по самому словарю,
   не по прототипу, обе цифры измерены `_dev/check_contrast.js`:
   - `.badge-neutral` (`fg-muted` на `surface-subtle`, лестница `kit.css`) — **4,3:1** в Light при
     7,0:1 в Dark. Для бейджа это ниже цели ≥7:1, которую D-020 ставит палитровым тинтам. Я всё
     равно взял эту лестницу (решение 4), потому что она есть в ките, но порог она не проходит.
   - `--one-info` как **текст** статуса — 4,2:1 Light и **3,2:1 Dark**. §1 предписывает для статуса
     в тексте именно `--one-info` (в отличие от success, где взят `-icon`); шага `--one-info-icon`
     в теме нет — он равен `--one-info`. То есть для info легко читаемого варианта в словаре
     просто нет.

6. **Опции `<select>` в браузерах без `appearance: base-select`.** `native.css` стилизует
   `option:checked` только внутри `@supports (appearance: base-select)` — то есть в свежем Chromium.
   В остальных браузерах список опций рисует ОС, и лестница §2.9 физически недостижима. Это
   ограничение платформы, не нарушение, но в чеклисте §3 строка «выбранная опция каждого `<select>` —
   strong-заливка» выполнима не везде, и это стоит отметить в самом правиле.

## 9. Отдельно: перескок панелей вверх (дефект v5, исправлен в v6)

Это не часть переделки — владелец сообщил об этом вместе с ней.

**Симптом.** Левая и центральная панели самопроизвольно прыгали в начало: прокрутил центральную
панель к календарю — и после выбора дня или просто через некоторое время всё возвращалось наверх;
в левой панели то же при выборе нижнего расписания.

**Причина.** `paint()` заменяет `shell.innerHTML` целиком. Все прокручиваемые контейнеры при этом
создаются заново, то есть с `scrollTop = 0`. Поэтому «прыгало» на **любой** перерисовке: выбор
расписания, клик по дню календаря, отметка строки, переключение вкладки, сохранение. А
`setInterval(() => render(), 30000)` делал это вообще без действий пользователя — отсюда «или также
при каком-то таймауте автоматом». Дополнительно `el.focus()` при восстановлении фокуса сам
подкручивает контейнер, чтобы показать поле.

**Исправление** — три части:

1. Все восемь прокручиваемых областей помечены `data-scroll` (левый список, центральная панель,
   строки сетки, вкладки шапки, полоса вкладок, JSON, правая панель, высокий попап).
   `paint()` снимает смещения перед заменой DOM и возвращает после — `captureScroll` / `restoreScroll`.
2. Фокус восстанавливается через `focus({ preventScroll: true })`.
3. Таймер на 30 секунд больше не перерисовывает страницу. `tickLive()` обновляет только то, что
   зависит от времени: положение линии «сейчас», точки «активно сейчас» в списке и пилюлю в шапке.
   Полная перерисовка остаётся лишь на смену календарной даты — и её прокрутка уже переживает.
   Ради этого точки «активно сейчас» теперь всегда в разметке и скрываются атрибутом `hidden`,
   а не выпадают из неё, чтобы их можно было обновлять на месте.

**Проверка** — `node _dev/test_v6_scroll.js`, 40 проверок, все проходят. Среди них: round-trip
`captureScroll`/`restoreScroll`; реальный `paint()` с непустыми смещениями; девять сценариев ровно из
описания дефекта (выбор «Рабочих часов» и «Ночной смены», два клика по дням календаря, смена вкладки,
отметка строки, смена активной строки, смена месяца, срабатывание таймера) — после каждого смещения
обеих панелей сохраняются; таймер на 30 с больше не вызывает `render`; пять срабатываний `tickLive`
подряд не сдвигают прокрутку; и сверка, что **ни один** прокручиваемый контейнер из CSS не забыт —
их ровно восемь, и все помечены.
